## Scoped but deferred features

- **User profiles and authentication** — deliberately saved for one of the *last* things to build, not because it's unimportant but because adding it early would block day-to-day development flow (every test/debug pass would have to go through login, multi-user state, etc.) before the base app's actual features are fleshed out. Revisit once the core feature set feels done.
- **Receipt/barcode scanning for piece-labeled ingredients** (Sept 15) — the manual "add to pantry" screen (`mobile/app/pantry/add_by_ingredient.tsx`) now adds piece-based ingredients (steak, fillet, ...) as one row per physical piece, each with its own weight and a price split proportional to weight (see `[[whole-unit-deduction]]`/`pieceLabel` in memory). The receipt scanner and barcode scanner haven't been revisited to match — a scanned line still becomes a single pantry entry with one blended weight, so a receipt showing "3 steaks, $18.47" has no per-piece weights to split across. Probably the right shape: let the receipt-review screen split one matched line into N rows the same way the manual screen now does, when the matched ingredient has a `pieceLabel`. Not started.
- **Expandable meal-prep sub-ingredients in recipe detail view** (Sept 15) — a recipe that uses a meal-prep as one of its ingredients (e.g. "Sous Vide Seared Filet Mignon" uses 1 bag of "Vacuum-Sealed Filet Mignon", itself produced by "Sous Vide Filet Mignon Prep") currently shows that meal-prep as a single flat ingredient row in `app/recipes/[id].tsx`'s ingredient list (~line 733) — no way to see what's actually inside it without separately opening the prep recipe. Ingredient already has `isMealPrep` + `productionRecipe` (a reference to the recipe that produces it, `server/models/Ingredient.js`), so the data needed to look this up already exists. Idea: when a row's ingredient has `isMealPrep`, add a chevron/expand affordance that shows that `productionRecipe`'s own `ingredientList` nested underneath (read-only, no need to fetch full recipe detail — just its ingredient list, name-only or with the same recursive expand if a prep is nested inside another prep). Not started.
- **Whole-piece matching not yet applied to Chilean Sea Bass** (Sept 15, checked per request) — "Sous Vide Miso Chilean Sea Bass Prep" (the raw-fish production recipe, analogous to "Sous Vide Filet Mignon Prep") still has its "Chilean Sea Bass" ingredient line at a fixed `matchMode: "quantity"`, `quantity: 226, unit: "g"` — the same "fixed weight of ingredient" pattern originally flagged as wrong for Filet Mignon before `wholePieceMatching` (see `[[whole-unit-deduction]]`) was built and that recipe converted. Filet Mignon's own prep recipe *is* already converted (`matchMode: "wholePiece"`, 250-400g range, `unit: "steak"`) — Sea Bass was never touched. Also, the "Chilean Sea Bass" ingredient itself has `pieceLabel: null` (unlike Salmon Fillet/Tuna Steak/Filet Mignon, which all got `pieceLabel: "fillet"`/`"steak"`) — would need a `pieceLabel` (probably `"fillet"`) too if converted, for pantry-list piece counting to work the same way. The consumer-facing "Sous Vide Seared Miso Chilean Sea Bass" recipe is fine as-is (correctly uses `matchMode: "quantity"` for its "1 bag" of the already-portioned meal-prep output — same pattern as the Filet Mignon final dish). Not started — needs a real min/max weight range decision for a sea bass fillet before converting (same DB-migration approach as `convert_to_whole_piece.js` used for the other recipes).
- **Real production tracking for pre-batched meal preps** (Sept 15, `WholePieceGrouping` branch — Phase 2, deliberately deferred from Phase 1) — see `[[whole-unit-deduction]]` for the full writeup. Phase 1 (this branch) fixed the resolve-sources picker for the *live* "cook fresh, no bag pre-stocked" path, where confirming e.g. "Sous Vide Seared Filet Mignon" with zero bags in stock already correctly substitutes down to the real raw steak (`expandProducedIngredientRows`) and the exact real weight already flows through to logged nutrition (`computeConfirmedRecipeNutrition` is deduction-source-agnostic — already correct, verified by code trace, no changes needed there). But confirmed with the user: pre-batching *is* a real workflow (cooking several sous-vide bags ahead and storing them) — and today there is no "run production" action anywhere in the app. The only way a bag ever enters pantry stock ahead of time is manually logging it through `pantry/add_by_ingredient.tsx`, completely disconnected from which real steak made it — every pre-batched bag silently carries the `Ingredient`'s generic nutrition value (`PantryItem` has no per-instance nutrition field at all today). To fix for real:
  - **Schema**: `PantryItem.nutritionMultiplier` (new field, default 1 / null) — the ratio between the real consumed piece's weight and the recipe's reference weight (the wholePiece line's `pieceMinWeight`/`pieceMaxWeight` midpoint — the same anchor `calcNutrition`'s snapshot-estimate branch already uses). `computeConfirmedRecipeNutrition` (`mobile/src/utils/mealPlan.ts`) would need to multiply by this whenever a deduction's `pantryItem` carries one, on top of its existing amount-based scaling.
  - **New "Produce a batch" action** — `app/recipes/[id].tsx`'s "Prepares" section is currently just a passive label/link to the producing recipe; it would need to become a real flow: pick how many to make → reuse the *same* Phase-1 weight-grouped picker to choose which real raw pieces to consume → for each one, deduct it and create one new output `PantryItem` stamped with that piece's own `nutritionMultiplier` → any non-wholePiece prep ingredients (herbs, oil, etc.) deduct scaled to the batch size, same math `expandProducedIngredientRows` already does for substitution.
  - **Open design question, not yet resolved**: is a prep recipe's yield always a clean 1-raw-piece-in → 1-produced-unit-out ratio (true for "Sous Vide Filet Mignon Prep" as far as checked), or can it differ? That determines whether each produced item can cleanly inherit one specific piece's weight 1:1, or whether a batch run needs to blend multiple source pieces into one shared multiplier for a single output unit — needs settling before implementation starts.
  - Not started — this is a real new feature (new UI flow + schema field), not a bug fix, and was deliberately scoped out of the `WholePieceGrouping` branch to keep that one small and low-risk.
