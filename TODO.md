## Known issues (pinned, not urgent)

- **Done: barcode scan pre-filling serving size with the whole package amount** (Sept 19) — was NOT a wrong-variable bug (checked several real Open Food Facts spice/condiment products via their API directly — `serving_quantity` was either a genuinely small, correct value, or simply `null`; never found a case where it equaled the package total). The real cause: whenever OFF had no usable `serving_quantity` at all (the common case for bulk/dry goods like spice jars), `BarcodeScannerModal.tsx` fell back to a hardcoded `100` — meant only as an internal reference amount for scaling the `_100g`-suffixed nutrition fields — and that same fallback number silently leaked out as if it were a real per-serving default, into `add_manual.tsx`'s `defaultPortionAmount` field and `receipts/review.tsx`'s row. Fixed by adding a new `ScannedProduct.servingIsEstimated` flag (true whenever there's no real declared serving, or — per the sanity check requested — the declared serving is `>= 90%` of the package total, which would also catch genuine mislabeling if it ever occurs) that all three consumers (`add_manual.tsx` both the direct-apply and router-param paths, `PantryMainPage.tsx`, `receipts/review.tsx`) now check before copying `servingSize` into a form field — an estimated value now just leaves the field blank for the user to fill in, instead of overwriting it with a fabricated number. The "amount added to pantry" field was already unaffected by this bug for the *new-ingredient* path — it's sourced from OFF's separate `product_quantity` field, which checked out fine across every real product tested. **Follow-up bug, same day, found via live testing:** the *existing-ingredient* path (scanning a barcode that already matches something in the catalog) had a related but distinct issue — `PantryMainPage.tsx`'s `scanContext === "pantry"` branch, on a match, only forwarded `ingredientId` to `pantry/add_by_ingredient.tsx` and dropped the scanned product entirely, so that screen fell back to its own no-scan default: the ingredient's `defaultPortionAmount`/`defaultPortionUnit` (a single-serving size, e.g. "15 ml" for fish sauce) — correct for someone manually logging one use, wrong for someone who just scanned the actual bottle they bought. Fixed by forwarding `product.packageQuantity`/`packageUnit` as `scannedQuantity`/`scannedQuantityUnit` params, which `add_by_ingredient.tsx` now prefers over the ingredient's default when present.
- **Done: tapping a text field now scrolls it into view** (Sept 20-22) — built as two shared hooks, `mobile/src/hooks/useScrollToFocusedField.ts` (low-level: given a scrollRef + a zero-size `collapsable={false}` anchor View rendered as the first child of the scroll content, measures a field and scrolls it near the top) and `useScrollFocusSection.ts` (the ergonomic wrapper screens actually use — bundles a ref/zIndex-carrying `wrapperProps` plus a `trigger` for the field's `onFocus`/`onOpen`). Two real, non-obvious bugs found live-device-testing before this worked: (1) `measureLayout(relativeTo, ...)` fails outright on this RN/Fabric version regardless of target — switched to two `measureInWindow` calls (anchor + field) and diffed them instead, which sidesteps the "relative to" relationship entirely; (2) a bare `<View>` with no other props can get optimized out of the native tree ("view flattening") under the new architecture, silently breaking measurement — fixed with `collapsable={false}` on the anchor and every field wrapper. Also surfaced and fixed a real, previously-invisible bug this exposed: `SearchableObjectDropdown`'s open option list only outranked its own immediate siblings (e.g. Brand vs. Generic side by side), not later unrelated sections further down the same ScrollView — plain RN/Yoga stacking paints later siblings over earlier ones by default, so an open dropdown was painting *underneath* content below it. Was invisible before because a focused field used to land near the bottom of the screen with nothing else visible below it; became obvious the moment scroll-to-focus started bringing fields near the top. Fixed with descending `zIndex` per section (see `useScrollFocusSection`'s own doc comment for the exact rule). Also fixed while in there: `SearchableObjectDropdown` and `CreatableMultiTagDropdown` never closed their option list on blur (tap away), only on select/Enter — both got `onBlur`. Rolled out to all ~13 real form pages (receipts/review, ingredients add/edit, pantry add/edit, meals add/edit, recipes add/edit, restaurant-meals add/edit, health goals/weight, settings kitchen) plus `onFocus`/`onOpen` passthrough added to `PriceInput`, `QuantityServingInput`, `DurationValueInput`, `DurationExpiryInput`, `SettingsNumericInput`. Deliberately skipped: `CreatableStringDropdown`/`UnitFamilyDropdown` (Modal-based popups, already immune to both bugs above since they render in an OS-level overlay, not inline).
- **Done: per-pantry-item deduction history** (Sept 22) — new ask, not previously scoped anywhere. `GET /api/pantry/:id/deductions?days=30` (`server/routes/PantryRoutes.js`) finds every confirmed `MealPlanEntry` whose `stockDeductions` drew from that pantry item within the window and returns date/slot/amount/source (whichever of meal/recipe/ingredient was actually logged). `PantryItemCard` (shared by the Pantry tab and the storage-location detail page) now expands in place on tap instead of navigating straight to edit — shows the item's full details (location, purchase date, expiry, price, store, notes) plus this deduction list (fetched lazily on first expand), with a separate explicit "Edit details" button inside the expanded view for the old navigate-to-edit behavior.
- **Receipt-review units aren't fully reliable yet** (Sept 6) — after fixing the barcode-scanner's quantity-not-updating and wrong-liquid-nutrition bugs, live-tested the receipt scanner end to end and it's functioning but "not perfect" per real-device testing — units still don't come out right in every case. Not yet diagnosed further; revisit with fresh real-receipt/barcode examples of what specifically comes out wrong.

- **Planning a meal-prep day through the planner** (Sept 16, flagged during the `WholePieceGrouping` work, deliberately deferred — "something we can work on later, especially when we have a full calendar fleshed out") — related to the item above but a different gap: that one is about `app/recipes/[id].tsx`'s "Cook now" action; this one is about the meal *planner* itself. Today, nothing stops you from adding a prep recipe (e.g. "Sous Vide Filet Mignon Prep," "Okonomiyaki Meal Prep Mix") to a day in the planner — and doing so has real, currently-useful upside (it shows up on your calendar, and `handleAddMissingToGroceryList` will correctly add its raw ingredients to the shopping list, same as any other recipe entry). The `[[whole-unit-deduction]]` badge shipped alongside this note (a small "Prep" tag in the add-recipe picker) helps you tell a prep recipe apart from its finished/eaten counterpart at a glance, but doesn't change what happens when you actually *confirm* one — and confirming is where it's wrong: today it's treated exactly like eating a dish — deducts the raw ingredients from pantry **and** adds the recipe's nutrition to that day's calorie/macro totals. Prepping isn't eating, so a confirmed prep entry should:
  - **Not** contribute to the day's logged nutrition at all (it's not a meal).
  - Still deduct the raw ingredients from pantry (as it already does).
  - **Additionally** create the produced item as new pantry stock — i.e. actually behave like "Cook now" (`handleConfirmBatch`, same file) rather than a bare recipe confirm that just consumes inputs with no output. Ideally reusing whatever comes out of the item above (`PantryItem.nutritionMultiplier`), so the newly-stocked bag/mix already carries accurate real-weight-derived nutrition for whenever it's actually eaten later.
  - Open design questions, genuinely unresolved: how does a `MealPlanEntry` even signal "this is a prep, not a meal" — a flag on the entry, or inferred purely from whether the recipe is in `producingRecipeIds`? Does a prep entry need its own status/slot semantics (a prep isn't "breakfast," "lunch," etc. in any meaningful sense) or a different confirm action entirely, separate from the normal eat-and-log confirm? How does this interact with the storage-location/expiry-date questions `handleConfirmBatch`'s batch card already asks, which the planner's confirm flow currently has no equivalent step for?
  - Deliberately not scoped further than this — per direct request, revisit once the planner's calendar/scheduling side of the app is more fully built out, since "plan a prep day" is fundamentally a calendar-shaped feature and the calendar itself is still evolving.

- **Two different meanings of "rating," don't conflate them** (Sept 16-17, flagged during the `WholePieceGrouping` rating work — see `[[meal-rating-system]]`) — `Recipe.scores`/`Dish.scores`/the new `Ingredient.scores` (mirrors the same shape, `server/models/Ingredient.js`) all mean one specific thing: *meal-satisfaction* — how much the user enjoyed eating this, captured at meal-plan confirm time, meant as one input (alongside planner history, nutrition, pantry state) for the still-deferred food recommender (see `[[food-recommender-design]]`). That is a genuinely different axis from *product/ingredient quality* — e.g. "these russet potatoes from this specific store are consistently good" — which is a fact about a specific product/source, not about how satisfying it was as a meal. Concretely raised because `Ingredient.scores` now technically accepts a rating for any ingredient via the API (no server-side restriction, matching `Recipe.scores`' own precedent of allowing a manually-added score with `mealPlanEntry: null`) — but no UI exists today to add one outside the meal-plan confirm flow, so this is a latent risk, not a live bug.
  - **Decision, not yet built**: if/when a product-quality rating is wanted, it should **not** reuse `Ingredient.scores` — different field name entirely, most likely anchored on `Brand` rather than the generic `Ingredient` (a specific product/source is what has "quality," not the abstract ingredient concept — a loose potato from a farmer's market with no brand wouldn't have anywhere to attach it under `Ingredient`-level scoping), triggered by a different flow (pantry-logging or brand-editing, not confirming a planner entry), and always labeled distinctly in the UI ("Meal rating" vs. "Product quality") so a bare number is never ambiguous between the two.
  - Not scoped further, not started — recorded so this distinction doesn't get lost and `Ingredient.scores` doesn't accidentally get overloaded to mean both things later.
