## In progress: Calendar section — modelled on Outlook for iPhone (branch `Calendar`, started Oct 3)

- **Repeating events (Oct 3):** a series is one record plus its rule; occurrences are computed per date range, never stored. Weekly repeats pick their days (`repeat.weekdays`). Editing or deleting an occurrence first asks **only this event / this and following / all events**. "Only this" adds the date to the series' `excludedDates` and saves the edit as a one-off event with `seriesId` + `originalDate` (`POST /events/:id/detach`). "This and following" ends the series the day before and starts a new series from there (`POST /events/:id/split`, or `DELETE ?from=` to delete). Deleting a series also deletes its split-off one-offs. The form opens on the tapped occurrence.

## Known issues (pinned, not urgent)

- **Done: barcode scan pre-filling serving size with the whole package amount** (Sept 19) — was NOT a wrong-variable bug (checked several real Open Food Facts spice/condiment products via their API directly — `serving_quantity` was either a genuinely small, correct value, or simply `null`; never found a case where it equaled the package total). The real cause: whenever OFF had no usable `serving_quantity` at all (the common case for bulk/dry goods like spice jars), `BarcodeScannerModal.tsx` fell back to a hardcoded `100` — meant only as an internal reference amount for scaling the `_100g`-suffixed nutrition fields — and that same fallback number silently leaked out as if it were a real per-serving default, into `add_manual.tsx`'s `defaultPortionAmount` field and `receipts/review.tsx`'s row. Fixed by adding a new `ScannedProduct.servingIsEstimated` flag (true whenever there's no real declared serving, or — per the sanity check requested — the declared serving is `>= 90%` of the package total, which would also catch genuine mislabeling if it ever occurs) that all three consumers (`add_manual.tsx` both the direct-apply and router-param paths, `PantryMainPage.tsx`, `receipts/review.tsx`) now check before copying `servingSize` into a form field — an estimated value now just leaves the field blank for the user to fill in, instead of overwriting it with a fabricated number. The "amount added to pantry" field was already unaffected by this bug for the *new-ingredient* path — it's sourced from OFF's separate `product_quantity` field, which checked out fine across every real product tested. **Follow-up bug, same day, found via live testing:** the *existing-ingredient* path (scanning a barcode that already matches something in the catalog) had a related but distinct issue — `PantryMainPage.tsx`'s `scanContext === "pantry"` branch, on a match, only forwarded `ingredientId` to `pantry/add_by_ingredient.tsx` and dropped the scanned product entirely, so that screen fell back to its own no-scan default: the ingredient's `defaultPortionAmount`/`defaultPortionUnit` (a single-serving size, e.g. "15 ml" for fish sauce) — correct for someone manually logging one use, wrong for someone who just scanned the actual bottle they bought. Fixed by forwarding `product.packageQuantity`/`packageUnit` as `scannedQuantity`/`scannedQuantityUnit` params, which `add_by_ingredient.tsx` now prefers over the ingredient's default when present.
- **Done: tapping a text field now scrolls it into view** (Sept 20-22) — built as two shared hooks, `mobile/src/hooks/useScrollToFocusedField.ts` (low-level: given a scrollRef + a zero-size `collapsable={false}` anchor View rendered as the first child of the scroll content, measures a field and scrolls it near the top) and `useScrollFocusSection.ts` (the ergonomic wrapper screens actually use — bundles a ref/zIndex-carrying `wrapperProps` plus a `trigger` for the field's `onFocus`/`onOpen`). - **Two different meanings of "rating," don't conflate them** (Sept 16-17, flagged during the `WholePieceGrouping` rating work — see `[[meal-rating-system]]`) — `Recipe.scores`/`Dish.scores`/the new `Ingredient.scores` (mirrors the same shape, `server/models/Ingredient.js`) all mean one specific thing: *meal-satisfaction* — how much the user enjoyed eating this, captured at meal-plan confirm time, meant as one input (alongside planner history, nutrition, pantry state) for the still-deferred food recommender (see `[[food-recommender-design]]`). That is a genuinely different axis from *product/ingredient quality* — e.g. "these russet potatoes from this specific store are consistently good" — which is a fact about a specific product/source, not about how satisfying it was as a meal. Concretely raised because `Ingredient.scores` now technically accepts a rating for any ingredient via the API (no server-side restriction, matching `Recipe.scores`' own precedent of allowing a manually-added score with `mealPlanEntry: null`) — but no UI exists today to add one outside the meal-plan confirm flow, so this is a latent risk, not a live bug.
  - **Decision, not yet built**: if/when a product-quality rating is wanted, it should **not** reuse `Ingredient.scores` — different field name entirely, most likely anchored on `Brand` rather than the generic `Ingredient` (a specific product/source is what has "quality," not the abstract ingredient concept — a loose potato from a farmer's market with no brand wouldn't have anywhere to attach it under `Ingredient`-level scoping), triggered by a different flow (pantry-logging or brand-editing, not confirming a planner entry), and always labeled distinctly in the UI ("Meal rating" vs. "Product quality") so a bare number is never ambiguous between the two.
  - Not scoped further, not started — recorded so this distinction doesn't get lost and `Ingredient.scores` doesn't accidentally get overloaded to mean both things later.
