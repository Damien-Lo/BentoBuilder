## Scoped but deferred features

- **User profiles and authentication** — deliberately saved for one of the *last* things to build, not because it's unimportant but because adding it early would block day-to-day development flow (every test/debug pass would have to go through login, multi-user state, etc.) before the base app's actual features are fleshed out. Revisit once the core feature set feels done.
- **Receipt/barcode scanning for piece-labeled ingredients** (Sept 15) — the manual "add to pantry" screen (`mobile/app/pantry/add_by_ingredient.tsx`) now adds piece-based ingredients (steak, fillet, ...) as one row per physical piece, each with its own weight and a price split proportional to weight (see `[[whole-unit-deduction]]`/`pieceLabel` in memory). The receipt scanner and barcode scanner haven't been revisited to match — a scanned line still becomes a single pantry entry with one blended weight, so a receipt showing "3 steaks, $18.47" has no per-piece weights to split across. Probably the right shape: let the receipt-review screen split one matched line into N rows the same way the manual screen now does, when the matched ingredient has a `pieceLabel`. Not started.
- **Whole-piece matching not yet applied to Chilean Sea Bass** (Sept 15, checked per request) — "Sous Vide Miso Chilean Sea Bass Prep" (the raw-fish production recipe, analogous to "Sous Vide Filet Mignon Prep") still has its "Chilean Sea Bass" ingredient line at a fixed `matchMode: "quantity"`, `quantity: 226, unit: "g"` — the same "fixed weight of ingredient" pattern originally flagged as wrong for Filet Mignon before `wholePieceMatching` (see `[[whole-unit-deduction]]`) was built and that recipe converted. Filet Mignon's own prep recipe *is* already converted (`matchMode: "wholePiece"`, 250-400g range, `unit: "steak"`) — Sea Bass was never touched. Also, the "Chilean Sea Bass" ingredient itself has `pieceLabel: null` (unlike Salmon Fillet/Tuna Steak/Filet Mignon, which all got `pieceLabel: "fillet"`/`"steak"`) — would need a `pieceLabel` (probably `"fillet"`) too if converted, for pantry-list piece counting to work the same way. The consumer-facing "Sous Vide Seared Miso Chilean Sea Bass" recipe is fine as-is (correctly uses `matchMode: "quantity"` for its "1 bag" of the already-portioned meal-prep output — same pattern as the Filet Mignon final dish). Not started — needs a real min/max weight range decision for a sea bass fillet before converting (same DB-migration approach as `convert_to_whole_piece.js` used for the other recipes).
- **Real production tracking for pre-batched meal preps** (Sept 15/16, `WholePieceGrouping` branch — Phase 2, deliberately deferred from Phase 1) — see `[[whole-unit-deduction]]` for the full writeup. **Correction (Sept 16): a production flow already exists** — `app/recipes/[id].tsx`'s "Cook now" ("Prepares" section) already reuses the full deduction/ambiguity pipeline (`buildIngredientRequirements`, the resolve-sources picker, `deductFromPantryItem`) and already calls `addIngredientToPantry` to create the produced item. The earlier note here calling this "no production action exists at all" was wrong — it does, and the remaining gap is narrower than described: `addIngredientToPantry` (in `handleConfirmBatch`) always stamps the new batch with the ingredient's flat/generic nutrition, with no memory of which real wholePiece weight(s) fed it. To fix for real:
  - **Schema**: `PantryItem.nutritionMultiplier` (new field, default 1 / null) — the ratio between the real consumed piece's weight (from `pendingInstructions`, already available in `handleConfirmBatch`) and the recipe's reference weight (the wholePiece line's `pieceMinWeight`/`pieceMaxWeight` midpoint). `computeConfirmNutrition` (`mobile/src/utils/mealPlan.ts`) would need to multiply by this whenever a deduction's `pantryItem` carries one, on top of its existing amount-based scaling.
  - **Wire into the existing "Cook now" flow** — no new UI needed, just compute the multiplier from `pendingInstructions`' real wholePiece amounts inside `handleConfirmBatch` and pass it to `addIngredientToPantry`.
  - **Open design question, not yet resolved**: is a prep recipe's yield always a clean 1-raw-piece-in → 1-produced-unit-out ratio (true for "Sous Vide Filet Mignon Prep" as far as checked), or can it differ? That determines whether each produced item can cleanly inherit one specific piece's weight 1:1, or whether a batch run needs to blend multiple source pieces into one shared multiplier for a single output unit — needs settling before implementation starts.
  - Not started — deliberately scoped out of the `WholePieceGrouping` branch to keep it small and low-risk.
- **Planning a meal-prep day through the planner** (Sept 16, flagged during the `WholePieceGrouping` work, deliberately deferred — "something we can work on later, especially when we have a full calendar fleshed out") — related to the item above but a different gap: that one is about `app/recipes/[id].tsx`'s "Cook now" action; this one is about the meal *planner* itself. Today, nothing stops you from adding a prep recipe (e.g. "Sous Vide Filet Mignon Prep," "Okonomiyaki Meal Prep Mix") to a day in the planner — and doing so has real, currently-useful upside (it shows up on your calendar, and `handleAddMissingToGroceryList` will correctly add its raw ingredients to the shopping list, same as any other recipe entry). The `[[whole-unit-deduction]]` badge shipped alongside this note (a small "Prep" tag in the add-recipe picker) helps you tell a prep recipe apart from its finished/eaten counterpart at a glance, but doesn't change what happens when you actually *confirm* one — and confirming is where it's wrong: today it's treated exactly like eating a dish — deducts the raw ingredients from pantry **and** adds the recipe's nutrition to that day's calorie/macro totals. Prepping isn't eating, so a confirmed prep entry should:
  - **Not** contribute to the day's logged nutrition at all (it's not a meal).
  - Still deduct the raw ingredients from pantry (as it already does).
  - **Additionally** create the produced item as new pantry stock — i.e. actually behave like "Cook now" (`handleConfirmBatch`, same file) rather than a bare recipe confirm that just consumes inputs with no output. Ideally reusing whatever comes out of the item above (`PantryItem.nutritionMultiplier`), so the newly-stocked bag/mix already carries accurate real-weight-derived nutrition for whenever it's actually eaten later.
  - Open design questions, genuinely unresolved: how does a `MealPlanEntry` even signal "this is a prep, not a meal" — a flag on the entry, or inferred purely from whether the recipe is in `producingRecipeIds`? Does a prep entry need its own status/slot semantics (a prep isn't "breakfast," "lunch," etc. in any meaningful sense) or a different confirm action entirely, separate from the normal eat-and-log confirm? How does this interact with the storage-location/expiry-date questions `handleConfirmBatch`'s batch card already asks, which the planner's confirm flow currently has no equivalent step for?
  - Deliberately not scoped further than this — per direct request, revisit once the planner's calendar/scheduling side of the app is more fully built out, since "plan a prep day" is fundamentally a calendar-shaped feature and the calendar itself is still evolving.
